  14. 800px: both rails become 44px drawer handles, and neither is a hidden feature. §3.3 / parity #42. The run handle keeps the run count and the inbox handle keeps its open count, so the two questions a closed rail would otherwise hide — how many runs, is anything waiting on me — are still answered on the strip. The alternative is one strip plus a top-bar inbox button, which is cheaper but splits the two rails into two different idioms.

At 800 the four number cells stay together — they are scanned as a block — and the gauge, which carries a shape rather than a number, gets the full 756px rather than being squeezed to ~200px where the hatched overshoot zone stops being legible. The run id and the liveness detail drop to their own line under the title so the title never truncates.

The lane label narrows 168 → 120px and the track 640 → 508px; every bar, notch, wait segment and grid line is recomputed from the same fixture times, so the trace is the 1440 trace drawn narrower — not a redrawn approximation. Rule on this: at 508px the two-minute grid is tight; the alternative is a four-minute grid below 900px.

An operator opening a dead run at 800px came for one decision — resume or delete — and at 1440 that card sits in the panel area below the fold. Here it is the first thing under the header, and it is the only accent-filled action on the screen (§3.7's action hierarchy: one primary per region). Rule on this: promotion is a layout difference between viewports, which the rest of this comp set avoids.
  19. 800px stale: bars stop where the engine did, orphaned agents are dimmed, and the time of death is stated as UNKNOWN. The two unfinished agents carry the orphaned mark (§6.4 step 8 / parity #58) and their bars end at the last event rather than being extended to "now" — a dead run has no "now". The died cell reads not recorded for the same reason: endedAt is written from a terminal run event and from nothing else (§6.2), and a run is stale precisely because it wrote none. An earlier revision of this frame said "died 26m ago", derived from the run.lock mtime. That was wrong and is withdrawn — the lock is created when the engine ACQUIRES the run, so its mtime dates the start; W6 exposes no death time and no lastSeenAt; and the shipped Home already renders this case honestly (AttentionStrip.tsx: "It wrote no terminal event, so there is no time of death to report"). Approving the old frame would have instructed W11 to contradict the live API and §6.5. Rule on this: "not recorded · started 1h10m ago" in the metric cell, versus dropping the cell entirely on a run that has no death time to show.
  20. The drawer is an overlay with a real scrim, not a rail that got narrow. §3.3 puts one breakpoint at 900px — the only one in this comp set, and the same one at 800 and at 480. Below it both rails become 44px handles, and tapping a handle slides its drawer over the page with a scrim across everything under the top bar. The scrim is click-to-dismiss and is an element, not a tint on the panel: the operator must be able to leave the drawer by pointing at the thing they were reading. The top bar stays uncovered so the run is still identifiable while the drawer is open. Rule on this: the scrim at ink 42%, and whether the drawer should come from the same edge as its handle (it does here) or always from the left.
  21. The §3.6 focus model, drawn. Opening moves focus to the drawer's HEADER, not to the first row — a roving-tabindex list that grabs initial focus makes the first run look selected. Escape closes and focus is restored to the 44px handle that opened it (§2.7: "Esc closes panel / drawer"), and so does choosing a run, so the operator never lands back at the top of the document. While the scrim is up the drawer is role="dialog" aria-modal="true" and Tab is contained inside it — the confirm dialog's trap (§3.6) generalized to any overlay, because a Tab that reaches the cockpit behind a scrim is a keyboard user operating a UI they cannot see.
  22. What the drawer does NOT do. It does not remember scroll position across opens (the selected run is scrolled into view instead), it does not animate wider than §3.4's 200ms panel slide, and prefers-reduced-motion replaces the slide with an instant swap while keeping the scrim — the scrim carries the "you are in an overlay" information and is not decoration. Rule on this: the drawer is 320px at 800 and 300px at 480, rather than full-bleed.
  23. 480px: the same breakpoint, not a new one. §3.3 names 900px and this comp set introduces no second threshold — 480 is drawn to show that the <900px rules bottom out somewhere real. What changes is only what fits: the header metrics wrap two per line, the budget gauge keeps its own full-width row (it carries a shape, not a number), and the tab row scrolls. All three tabs are still tabs — nothing moves into an overflow menu, at any viewport.
  24. 480px: the Gantt is neither dropped nor rescaled — it SCROLLS. The lane label narrows 170 → 104px and the plot keeps its 350px track, so the bars, notches, wait segments and grid lines are the same geometry as the 800px frame. Ruler, saturation strip and lanes scroll together in one horizontal scroller, so they never come off a common axis. The alternative — rescaling the track to the viewport — would mean two screenshots of the same run could not be compared, which is the one thing a timeline may not do. Rule on this: horizontal scroll versus a four-minute grid below 600px.
  25. 480px: the saturation strip stays, at full height. It is the Timeline tab's whole argument (Q5 — "raise --concurrency"), and a strip shrunk to a hairline is a conclusion nobody reads. It is the first thing that would go if the tab had to lose something; it does not have to, because the tab scrolls. The run table at 480 is where something genuinely goes: its rows wrap into a two-line record (identity, then the numbers as a meta strip) and the column header row is dropped, because every remaining value is self-describing and a column label with no column is furniture.
