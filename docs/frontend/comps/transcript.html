Two gaps in the security matrix, both exploitable, ranked by severity.

1 — the token comparison is not constant-time

verifyReadToken at src/viewer/auth.js:71 uses ===. Node short-circuits string comparison on the first differing byte, so response latency leaks a prefix oracle. With the viewer bound to 127.0.0.1 this needs local code execution to exploit, which is exactly the threat the control token exists to bound.

  • Fix: timingSafeEqual on equal-length buffers, length-check first.
  • Test: assert the comparator identity, not the timing — a timing assertion is flaky in CI.

2 — the Host check accepts a trailing dot

127.0.0.1. is a distinct, valid Host that resolves identically and is not in the allowlist, so DNS-rebinding protection can be walked past.

Both findings are in auth.js. Neither is covered by the 144-test suite, so both would survive a green run.

Annotations — what to rule on
  1. Header answers "which agent, how far, how much" in one 11px mono strip. Facts are separated by hairlines rather than bullets so the row reads as an instrument readout. Lifetime usage (summed over every result record for this key — the same aggregation Journal.load uses to seed the budget) sits beside the attempt selector's per-attempt figures, and both are labelled. §2.5's Sol-13 vocabulary is enforced by that labelling: run invocation, execution attempt, provider turn.
  2. The prompt comes first, in full. E10 records the whole prompt; the block collapses to 15 lines with expand and copy. This is the single most common "what did you actually ask it" question, and most viewers make it unanswerable. The footer note says nothing was truncated — a claim the UI can only make because the cap marker is absent.
  3. Reasoning collapses to a one-line preview, not to a bare "reasoning" pill. The preview is the first sentence, so the block is skippable without being opaque. Left border rather than a full tint: reasoning is content, not state.
  4. Tool calls are paired to results by id (E11), and the id is shown. The id toolu_… chip is dotted, not solid, because it is provenance rather than data. On old runs the pairing falls back to a position stack and the chip reads approximate. Rule on this: is the id chip worth its pixels on every card, or should it appear only when the pairing is approximate?
  5. Terminal cards sit on the fixed dark well in both themes — toggle the theme and the well does not move (§3.2, decision final). The command clamps to two lines; a mouseup that follows a text selection does not toggle it (#73). "exit code 1" renders only because the adapter reported one; when no code exists the line is omitted entirely rather than fabricated from isError ? 1 : 0. Cards break out past the 88ch prose column to panel width.
  6. File-change cards carry a computed +N −M tally and a five-square bar (#79–#82): four actions with past-tense verbs, addition/deletion/hunk line classes, and an explicit "no diff available" card when the tool wrote a file but returned nothing to synthesize a diff from. An empty card would have read as "no changes".
  7. The answer is safe-by-construction markdown (§9.7): headings, lists, blockquote, inline code, fenced code with a language chip and copy. Raw HTML renders as literal text and images render as link chips — never fetched. Prose is 14px/1.45 capped at 88ch because a reviewer's finding is read, not scanned.
  8. The steer composer is the region's one accent action, and it is enabled only because the folded state is exactly running (critique M11). The working indicator reads "Thinking…" after reasoning and "Working…" otherwise (parity #95), and is never shown inside a dead run (#58). Delivery verdicts toast inline and append to the timeline, which is why the operator steer at 14:15 is a permanent row.
  9. Both rails are collapsed to icon strips here — 48px and 44px — because the transcript is what you came for. The inbox strip keeps its unread count so a question arriving mid-read is not silent. Rule on this: at 1440 the 55/45 split leaves the transcript 607px ≈ 73ch, under §3.3's 88ch maximum. Accept, or make the transcript the 55 side when it is open?
  10. The compare affordance is explicit rather than hidden in a menu. Judge-panel and adversarial-verify workflows are the entire point of flowition, so ?a=3 opens a second panel side by side — comparison must not require two windows. THIS frame is the state before the comparison — one transcript beside the cockpit, with the candidate agent docked. The comparison itself is the next two frames, at both required viewports.
  11. 800px compare: the two panels are STACKED — the operator's ruling, and DESIGN §2.5 is amended to match. §2.5 now reads: side-by-side is normative at ≥900px, and below §3.3's single 900px breakpoint the compare renders as a stacked pair, full-width panels, sequential scroll. The arithmetic that decided it: both rails are 44px handles, so the compare column is 712px — side by side that is ~355px a pane, under the 607px the row types were designed at, so the SAME row wraps differently on the two sides and the eye compares two renderings instead of two answers. Stacked, both panes keep the full 712px and a row renders identically in both. The cost is scrollback: ~370px of height per pane, two to three rows each, and the two agents are never simultaneously at eye level — which is what annotation 12's shared pin bar is for. The side-by-side drawing is kept as ALTERNATIVE A in the next frame, so the ruling can be read beside what it rejected.
  12. 800px compare: the shared pin bar is what makes a narrow compare legible. The comparison an operator is making is "what did B do at the step where A did X". Both panes are anchored to the same step, so two ~355px columns show the same moment rather than each pane's own last scroll position — which is what stops a narrow side-by-side from becoming two unrelated feeds. The output-token delta sits on the same bar because it is the other thing a judge-panel reader wants at a glance, and it is the one number that is only meaningful as a pair. Stacked, it does more work than it would side by side: the panes are never at eye level together, so the pin is the only thing that guarantees the two are showing the same moment. It is drawn identically in ALTERNATIVE A.
  13. 800px compare: the rails stay as 44px handles, not a top-bar menu. Same rule as the cockpit at 800 (cockpit.html annotation 14) — the two idioms must match, or the run rail means one thing on one screen and another thing on the next.
  14. 1440 compare: entering the comparison collapses BOTH rails to strips. 1440 − 48 − 44 = 1348, so each panel is 674px — past the 607px the row types were designed at, which is the whole point. Keeping the 280px run rail would give each panel 534px and reflow every card being compared. Rule on this: auto-collapsing the rails on entering compare, versus leaving them and letting the panels go under 607.
  15. The pair is the unit, so the pair has a header. One bar names both agents, owns Swap (\) and owns the single Close that ends the comparison; each panel keeps only what is about ITSELF — its own search, its own pin toggle, its own close.
